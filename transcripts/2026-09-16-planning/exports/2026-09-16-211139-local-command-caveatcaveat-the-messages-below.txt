  ❓ Q7 - PUT vs PATCH semantics: How do PUT and PATCH differ?
  - PUT: a full replace. Every writable field is required, including
    collectionId (a UUID or explicit null) and notes. It never creates, and
    returns 404 if the resource is missing.
  - PATCH: a partial update.
    - An absent field stays unchanged.
    - collectionId: null moves the Bookmark to Uncategorised.
    - null for any other field gets a 422.
    - An empty body {} is a 200 no-op.
  - Collections: the only writable field is name, so PUT and PATCH end up the
    same.

  Alternatives: PATCH as JSON Merge Patch (RFC 7396) or JSON Patch (RFC 6902).

  ➡️ As described above, with a plain application/json body, not merge-patch or
  JSON Patch. Leaving a field out and sending null stay two different things,
  which is all "move to Uncategorised" needs.

  ❓ Q8 - Error format and status codes: What do error responses look like, and
  which status codes do we use?
  - Format: everything is application/problem+json (RFC 9457).
  - 400: a syntactically bad request, meaning malformed JSON, unknown or
    forbidden fields, or bad query params.
  - 422: a request that is well-formed but has invalid values, such as a wrong
    type, too long, or a bad URL scheme. The body adds errors: [{ "pointer": 
    "/url", "detail": "…" }] (JSON Pointer).
  - Other codes: 409 for a name clash, 404 as already decided, and a generic 500
    with no details.

  The alternative is a single 400 for everything, in Nest's default {statusCode,
  message[], error} shape.

  ➡️ The split above. The SPA already expects 422 for field errors, and pointers
  map straight to form fields. The exception factory can tell apart
  class-validator's whitelistValidation errors, which become 400, from all other
  errors, which become 422.
