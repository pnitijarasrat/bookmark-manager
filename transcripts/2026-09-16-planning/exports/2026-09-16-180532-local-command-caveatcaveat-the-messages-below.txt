  ❓ Q1 - Where does the code exchange happen?

  (A) SPA as a public client. @auth0/auth0-react runs PKCE in the browser and
  holds the access token. It sends the token to the API as Authorization: Bearer
  …, and the API only checks tokens.

  (B) Backend-for-frontend (BFF). A server on port 3000 serves the SPA, handles
  /callback, and exchanges the code itself. It still has to use the public
  client with no secret, because that's how the tenant registers it. It keeps
  the tokens in a server-side session and gives the browser an HttpOnly cookie.
  - Gain: a page reload keeps you signed in for the token's 2-hour life, and no
    token ever reaches JavaScript.
  - Costs:
    - a session store
    - CSRF protection, because the cookie is sent automatically
    - a proxy in front of the API
    - /callback fixes the BFF to port 3000
    - it uses a client registered as an SPA in a way it wasn't designed for,
      which needs justifying in the write-up

  ➡️ (A) SPA as a public client. The tenant registered exactly that kind of
  client, and the SDK hardcodes S256. The API stays a plain resource server, and
  the brief's "OIDC on every route" becomes "every request carries a verified
  Bearer token", which is simple to test. The cost is the reload/persistence
  trade-off, which I'll ask about next round. (B) would only be worth it if you
  decide that "no token in JavaScript" and "survives a reload" both have to
  hold.

  ---

  ❓ Q2 - What does the API accept, and how does it check tokens?

  My proposed rule set uses jose's jwtVerify with the JWKS from
  createRemoteJWKSet:
  - algorithms: ['RS256'] only, so HS256 or PS256 tokens designed to trick the
    check are rejected.
  - issuer must be exactly https://dev-yg.us.auth0.com/, trailing slash
    included.
  - audience: 'https://bbl-candidate-test-api'. Because aud is an array, jose
    checks that it contains this value.
  - exp is required, with a small clock tolerance (e.g. 5 s).
  - sub must be a non-empty string.
  - The token is read from the Authorization: Bearer header only, never from a
    query string or cookie.

  Two parts are open:
  - Check that azp equals our client ID? The audience name suggests it's shared
    with other candidates' apps on this tenant. Those apps can get valid tokens
    for the same audience.
  - Check scope? The API defines no permissions, so there's nothing useful to
    check.

  ➡️ Yes to the azp check, no to the scope check. The azp check costs one line
  and makes the API accept only tokens issued to this SPA. Don't pin the sub
  format (auth0|…) in the guard. The guard's job is to check the token, and
  which Owners exist is the data layer's business.

  ❓ Q3 - How is "OIDC on every route" enforced?

  ❓ Q1 - How are tokens kept between page reloads?

  Tokens can't be renewed silently, so every option ends with an interactive
  Universal Login at some point. The choice is when that happens.

  - (a) Memory only, the SDK default. Any reload or new tab sends you back to
    Universal Login. JavaScript loaded after an XSS can't read old tokens from
    storage.
  - (b) cacheLocation: 'localstorage'. The token survives reloads and tabs until
    it expires after 2 hours. Any XSS can read it and use it for up to 2 hours.
  - (c) A custom sessionStorage cache. The token survives reloads in the same
    tab and is cleared when the tab closes. XSS can read it just as in (b).

  One fact is missing, and only a human can check it. In #13 we tested only
  prompt=none. We don't know whether an interactive redirect to Universal Login,
  made right after signing in, asks for the password again or signs you
  straight back in, perhaps after one click on the localhost confirmation. That
  decides how much (a) actually costs.

  ➡️ (a) Memory only. This project is judged on data isolation, and "no token in
  storage that XSS can read" is an easy rule to defend. The re-login on reload
  is a cost we name in the Decisions write-up, and it follows from facts about
  the tenant that we can't change. If the redirect check shows you have to type
  the password on every reload, I'd switch to (c). (b) keeps a token that gives
  up to 2 hours of access in every tab, and nothing needs that.

  ❓ Q5 - What happens when the token expires or the API returns 401?

  After 2 hours, or after any reload if you pick memory-only in Q1,
  getTokenSilently fails with consent_required or login_required.

  ➡️ Treat any failure from getTokenSilently, and any 401 from the API, the same
  way:
  - Call loginWithRedirect with appState: { returnTo: <current path> }.
  - /callback handles the redirect back and sends you to returnTo. Only same-app
    relative paths are allowed there, so it can't be used as an open redirect.

  ---

  ❓ Q6 - How does logout work?

  ➡️ Call client.logout({ logoutParams: { returnTo: 'http://localhost:3000' } 
  }). This clears the in-memory cache and goes through Auth0's /v2/logout, which
  ends the Auth0 session.

    can't be revoked. A token copied before logout keeps working until it
    expires, at most 2 hours later.

    that only checks tokens.
