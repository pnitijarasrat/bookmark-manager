  Round 1 covers the questions that don't depend on each other:

  ❓ Q1 - One rule for another Owner's IDs, everywhere: When a request names a
  resource that exists but belongs to someone else, should the API always behave
  exactly as if the resource didn't exist? That would cover every place an ID
  can appear:
  - A path ID in GET, PUT, PATCH or DELETE on /bookmarks/:id, /collections/:id
    or /collections/:id/bookmarks: always 404, never 403.
  - A collectionId in a Bookmark's request body: the same error as a Collection
    that doesn't exist. That's probably a 422 on the field, since the SPA shows
    422s next to the form (the exact status goes to #8).
  - A collectionId in a list filter: the same result as a Collection that
    doesn't exist.

  The alternative is 403 for resources that exist but aren't yours. That's more
  honest for debugging, but it tells the caller the resource exists.

  ➡️ Use one rule: another Owner's ID is treated as nonexistent wherever it
  appears, and the response is identical down to the byte (Q6 covers how). For
  list filters, return 200 with an empty list rather than a 404, since a filter
  that matches nothing isn't an error. The empty list looks the same for both
  cases, so it reveals nothing.

  ---

  ❓ Q2 - Where the Owner scope is applied: What stops a new query from
  forgetting the Owner? The options:
  - (a) A repository layer. Every method takes ownerId as a required first
    argument, and every where includes it. A lint boundary stops code outside
    the repository module from importing the Prisma client. This is simple and
    easy to read, but it's still enforced by convention inside the repository.
  - (b) A Prisma client extension. prisma.forOwner(sub) adds ownerId to every
    model operation. The catch: query extensions don't reach nested writes or
    $queryRaw, so there are gaps. It's also fairly magical.
  - (c) Postgres row-level security (RLS). Policies on both tables use owner_id 
    = current_setting('app.owner_id'). This is the only option where a forgotten
    filter still returns no rows. The costs:
    - Every request's queries run in a transaction that first calls
      set_config('app.owner_id', sub, true).
    - The app connects as a separate, restricted role. The table owner and
      superusers skip RLS unless FORCE ROW LEVEL SECURITY is set, so migrations
      and the seed use a different role.
    - Tests need to cover the RLS setup itself.
  - (d) A combination.

  ➡️ Choose (d): the repository layer from (a) with the lint boundary, plus RLS
  from (c) as a safety net. The repository's explicit ownerId keeps the code
  readable and testable. RLS gives #10 real structural proof: a test can run an
  unscoped query as the app role and show that it returns nothing. I'd skip (b),
  because it adds magic without closing the gaps that RLS closes.

  ---

  ❓ Q3 - ID scheme: The options:
  - Sequential integers: these leak counts and invite enumeration.
  - UUIDv4: random and opaque.
  - UUIDv7: sorts by time, which helps index locality, but the ID contains its
    creation time.
  - cuid2: needs an extra library and has no native Postgres type.

  ➡️ Use UUIDv4 in a native uuid column, generated by the database with
  @default(dbgenerated("gen_random_uuid()")). At this scale, UUIDv7's index
  benefit doesn't matter, and it's better not to leak creation times through
  IDs. The API already returns createdAt if we want it.

  ---

  ❓ Q4 - How a Bookmark's Collection gets the same Owner: The options:
  - (a) Only an application check, a scoped lookup before the write.
  - (b) Only a composite foreign key: Bookmark(collection_id, owner_id) → 
    Collection(id, owner_id), backed by a unique constraint on Collection(id, 
    owner_id).
  - (c) Both.

  One interaction with #9: if deleting a Collection sets its Bookmarks'
  collectionId to null, a plain composite foreign key would also null owner_id.
  Postgres 15+ avoids this with ON DELETE SET NULL (collection_id). Prisma's

  ➡️ Choose (c). The scoped lookup (under RLS, per Q2) gives a clean 422 for a
  Collection that doesn't exist or isn't yours. The composite foreign key
  guarantees the rule even if a code path skips the check. The hand-edited
  migration is a small, one-time cost, and I'd note it in DECISION.md. Whether
  deleting a Collection sets null or cascades stays with #9. The foreign key
  works with either.

  ---

  ❓ Q5 - Keeping ownerId out of client input: When a request body contains
  ownerId, or any other field the client can't set, should the API reject it
  with 400 or silently drop it? And should responses include ownerId at all?

  ➡️ Reject it with 400. Nest's global ValidationPipe gets whitelist: true, 
  forbidNonWhitelisted: true, and no request DTO has an ownerId field. Rejecting
  is better than silently dropping, because a client that thinks it can set the
  owner should find out. Responses also leave out ownerId: it's always the
  caller's own sub, so it tells them nothing, and leaving it out keeps sub
  values out of the API's responses.

  ---

  ❓ Q6 - Side channels: Which of these should this issue address?
  - Error bodies: the 404 is byte-identical for both cases. A fixed
    problem-details body never repeats the path or the ID, which fixes the
    archived attempt's instance bug.
  - Timing: each lookup is one query on id AND owner_id, so a resource that

  - Uniqueness constraints: any unique constraint on user content, such as

  - Out of scope here: logging and rate limiting belong to HTTP hardening.

  ➡️ Address all three: identical fixed bodies, single-query lookups, and only
  per-Owner uniqueness constraints. Leave logging and rate limiting to HTTP
  hardening. I wouldn't add artificial delays to even out timing: with a single
  query, the two cases are already on the same path.
