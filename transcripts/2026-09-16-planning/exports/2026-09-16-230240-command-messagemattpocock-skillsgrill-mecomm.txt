  ---

  ❓ Q1 - Where /me gets profile data (#6): The access token only carries sub.
  There are two ways to get the email:
  - (a) The API calls Auth0 /userinfo with the caller's Bearer token. Nobody has
    tried this from the server yet.
  - (b) The SPA reads the email from its ID token, and /me returns only what the
    API already knows.

  There's a catch with (a). The layout loader calls /me, and React Router
  re-runs loaders after every action. So every save would also call /userinfo,
  and Auth0 rate-limits that endpoint.

  ➡️ Use (a), since the brief wants /me to be a real API endpoint. Also:
  - Cache the /userinfo result in memory, keyed by a hash of the token, until
    the token's exp.
  - Give the layout route shouldRevalidate: () => false so saves don't re-run
    its loader.
  - Have a human check the server-side /userinfo call once before building on it
    (see Q9).

  ---

  ❓ Q2 - What /me returns (#6): Should the response include sub? We already
  keep ownerId (which is the sub) out of every response.

  ➡️ Return { email, name, picture } without sub, which matches the ownerId
  rule. If /userinfo leaves out a field, return null rather than dropping the
  key.

  ---

  ❓ Q3 - Seed data with only one real login (#11): Only one tenant user can
  sign in, but the brief asks for seed data for at least 2 Users.

  ➡️ The seed script:
  - Owner A: reads the real test user's sub from SEED_OWNER_A_SUB.
  - Owner B: uses a fixed placeholder, auth0|000000000000000000000000.
  - Contents: each Owner gets two Collections plus some Uncategorised Bookmarks.
  - Deliberate overlaps: both Owners have a Collection with the same name and
    some of the same URLs, so a leak would show up at once.
  - Reruns: it deletes and re-creates only those two Owners' rows.

  A reviewer who signs in sees only A's data, and the README shows how to
  confirm in psql that B's rows are there.
