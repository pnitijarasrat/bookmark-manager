  ❓ Q1 - What happens to a Collection's Bookmarks when the Collection is 
  deleted?

  - (a) Set-null: its Bookmarks become Uncategorised and nothing is lost.
  - (b) Cascade: its Bookmarks are deleted with it.
  - (c) Refuse while non-empty: the API returns 409, and the User has to move or
    delete the Bookmarks first.
  - (d) Client chooses: for example DELETE 
    /collections/:id?bookmarks=keep|delete.

  In this domain a Collection is a label on Bookmarks, not a container that owns
  them. The brief says Bookmarks belong to "zero or one" Collection, so
  Uncategorised is a normal state. Cascade can silently destroy many saved links
  in one click. Refuse makes deleting a Collection tedious, because the
  Collection dialog's Bookmark list is read-only (#12). Client-chooses doubles
  the API surface, the tests and the cross-Owner matrix for a choice the brief
  never asks for.

  ➡️ (a) Set-null. Deleting a Collection never deletes a Bookmark. It matches
  the archived attempt, and the foreign key rule is already planned.

  ---

  ❓ Q2 - Soft or hard delete, and is there an undo?

  - (a) Hard delete, no undo, with a confirmation dialog. This is how Bookmarks
    already work.
  - (b) Soft delete (deletedAt) with an undo Snackbar. Every Owner-scoped query
    would need a deletedAt IS NULL filter. That filter is one more thing the
    isolation layer can get wrong. Name uniqueness would need a partial index,
    and set-null would have to be undone as well, so we'd have to remember which
    Bookmarks were in the Collection.
  - (c) Hard delete with a client-side undo that re-creates the Collection. It
    would get a new ID and a new createdAt, and the SPA would have to re-assign
    each Bookmark, which is fragile.

  ➡️ (a) Hard delete with a confirmation, no undo. Bookmarks and Collections
  then behave the same way. The repository layer's single-query rules stay
  unchanged. If Q1 is set-null, no Bookmark is lost anyway, so an undo would
  only save the User from re-typing a name.

  ❓ Q3 - Where does the set-null happen?

  - (a) The database foreign key. The migration is hand-edited to ON DELETE SET 
    NULL (collection_id), and the repository runs a single delete({ where: { 
    id_ownerId } }), which turns P2025 into 404. It's atomic and needs only one
    statement. A Bookmark saved to this Collection at the same moment is covered
    by the P2003 → 404 handling that's already planned. The downside is a
    hand-edited migration that Prisma's schema can't express, and prisma migrate
    dev may report schema drift.
  - (b) The application, in one transaction: updateMany({ where: { ownerId, 
    collectionId }, data: { collectionId: null } }) and then the delete. It's
    plain Prisma with no hand-edited SQL. The foreign key stays RESTRICT as a
    safety net. The downsides are two statements, and a Bookmark created between
    them makes the delete fail with a foreign-key error, which then needs its
    own handling.

  ➡️ (a) The database foreign key. It's one atomic statement with no race to
  handle, and owner_id can't be nulled. We add a migration test that deletes a
  Collection and checks that the Bookmarks keep their owner_id and have
  collection_id = null. That test protects the hand edit.

  ---

  ❓ Q4 - Does set-null change the affected Bookmarks' updatedAt?

  updatedAt is Prisma's @updatedAt, which only changes when Prisma writes the
  row. If Q3 is (a), the database moves the Bookmarks and their updatedAt stays
  the same. To change it we'd need a trigger or option (b).

  ➡️ No, it stays the same. The User didn't edit those Bookmarks. Nothing sorts
  or filters by updatedAt. We write it down as a documented consequence so a
  reviewer doesn't read it as a bug.

  ❓ Q6 - What do the API and the SPA do after a delete?

    the Collection may already have been deleted in another tab. Any other
    failure shows a Snackbar. These follow the existing rules. No "Deleted"
    success Snackbar is shown.

  ➡️ Yes to both, as described.
