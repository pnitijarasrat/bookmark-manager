  ❓ Q1 - Add a caching library on top of loaders?: Loaders are already settled.
  The open question is whether to add TanStack Query as a cache behind them, or
  to use plain React Router loaders and actions and let the router reload the
  page's data after every action.

  ➡️ Plain loaders and actions, with no TanStack Query. The data is small and
  belongs to one User, and reloading after each action is correct by default. A
  second cache would bring its own invalidation bugs. Pending states come from
  useNavigation and useFetcher.

  ---

  ❓ Q2 - How "view one" is shown:
  - (a) Both /collections/:id and /bookmarks/:id are full pages.
  - (b) Both are child routes shown as a Dialog or Drawer over their list.
  - (c) A mix of the two.

  ➡️ (c):
  - /collections/:id is a full page. It is itself a list (via GET 
    /collections/:id/bookmarks) and reuses the Bookmark list component.
  - /bookmarks/:id is a child route of /bookmarks, shown as an MUI Dialog with 
    the view and edit form. The URL still links straight to it, closing the
    dialog goes back to the list, and the list keeps its scroll position and
    filters.

  ---

  ❓ Q3 - How the route guard works: Auth0's isLoading and isAuthenticated are
  React state, but loaders run outside React. The options:
  - (a) A <RequireAuth> wrapper component.
  - (b) A pathless protected layout route whose middleware or loader reads the
    auth state from the router context and redirects.

  In both cases the router must wait until Auth0 has finished loading.

  ➡️ (b), set up like this:
  - Wait for Auth0: don't create the router until isLoading is false, and show a
    full-screen spinner until then.
  - Pass the auth state in: put isAuthenticated into the router context
    alongside the getter.
  - Guard in one place: a pathless layout route's middleware throws
    redirect('/login?returnTo=…').

  This runs before any protected loader, so no loader ever runs without a token.
  Tests can pass a fake context. If RR 8.4's middleware API doesn't fit, a
  parent loader does the same job.

  ---

  ❓ Q4 - Token expiry and API 401s (left open in DECISION.md): tokens live only
  in memory and last 2 hours, and silent renewal returns consent_required. So
  after about 2 hours getAccessTokenSilently throws, or the API returns 401.
  What should happen then?
  - (a) Call loginWithRedirect straight away.
  - (b) Send the user to /login?returnTo=<current>&reason=expired, where the
    page shows "Your session expired, sign in again".
  - (c) Show a modal on top of the current page.

  ➡️ (b). One apiFetch helper handles both cases, the thrown getter error and a
  401 from the API: it clears the local auth state and throws that redirect.
  This matches the settled decision that we never jump straight to Universal
  Login. A half-filled form is lost; we accept that and record it as a
  consequence.

  ---

  ❓ Q5 - How 404s and other errors are shown: a loader gets a 404, either
  because the resource doesn't exist or because another Owner owns it. What does
  the user see, and what about 5xx or network failures?

  ➡️
  - 404: apiFetch throws data(null, { status: 404 }). A route error boundary
    shows the same "Not found" page in both cases, with a link back to the list,
    so another Owner's resource can't be told apart from a missing one.
  - 5xx or network failure: a generic error boundary with a "Try again" button
    that reloads the data.
  - Failed action: a 422 validation error is returned as action data and shown
    next to the form fields. Other errors go to a Snackbar.

  ---

  ❓ Q6 - Shared API types:
  - (a) OpenAPI generated from Nest (@nestjs/swagger plus its CLI plugin) →
    openapi-typescript and openapi-fetch in the SPA.
  - (b) A shared workspace package of zod schemas, used for validation in both
    Nest and the SPA.
  - (c) Hand-written types copied into both apps.

  ➡️ (a). The API is the source of truth. The spec also documents the API for
  reviewers. openapi-fetch gives typed paths, and a CI check can fail if the
  spec is out of date. This doesn't require a monorepo, so it doesn't depend on
  the repo-layout decision, which is still open. (b) ties the frontend to the
  backend's validation library, and (c) lets the two copies drift apart.

  ---

  ❓ Q7 - Create and delete-Bookmark flows: is creating done in a Dialog, an
  inline form or a separate /new route? Does deleting a Bookmark need a
  confirmation dialog, or is it immediate with an undo Snackbar?

  ➡️
  - Create: a "New" button opens an MUI Dialog that submits through a fetcher to
    the list route's action. There's no /new route.
  - Delete a Bookmark: a confirmation dialog, because the API has no undo; that
    depends on #9's soft-vs-hard delete choice. If #9 adds soft delete, we'll
    revisit the undo Snackbar.
  - Delete a Collection: waits for #9.

  ---

  ❓ Q8 - App shell: how does the user move between /collections and /bookmarks,

  ➡️ A protected layout route holds everything:
  - Top bar: an MUI AppBar with the app name.
  - Navigation: two tabs linked to the routes, "Collections" and "Bookmarks".
  - Account: an avatar menu on the right with "Sign out", which calls the
    settled logout.
  - Landing: / sends signed-in users to /collections.

  What the avatar and menu show waits for #6.
