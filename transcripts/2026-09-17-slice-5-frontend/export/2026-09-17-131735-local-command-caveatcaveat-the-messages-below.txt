  frontend slice) finished with 5 findings. None are high severity, and none
  were reproduced in a browser.

  1. frontend/src/api/api-fetch.ts:176 (medium): the page cursor ends up in the 
     page URL after sign-in.
     - If the session expires during a "Load more" click, the saved return path
       includes the list cursor (/bookmarks?...&cursor=X).
     - After signing in again, the user lands on page 2 as though it were the
       first page. The Collection filter, the picker and the chips all show up
       empty.
     - Later filter changes keep the cursor in the URL, which breaks our rule
       that the cursor never goes there.
     - Fix: remove cursor from the path before calling loginPath.
  2. frontend/src/api/api-fetch.ts:180-184 (low/medium): any token error signs 
     the user out.
     - A brief network drop while fetching a token calls clearSession() and
       sends the user to /login?reason=expired. They should see the "Couldn't
       reach the server" error instead.
     - Fix: only treat Auth0's login_required, consent_required and
       missing-refresh-token errors as an expired session.
  3. frontend/src/lists/load-more.tsx:637 (low): a validation error resets the 
     list to page 1.
     - The dialog actions return failed results (422, 409, collection-not-found)
       with status 200. React Router then re-runs every loader, which throws
       away the pages loaded with "Load more" and fetches all Collections again.
     - Fix: return these results with their 4xx status (data(result, { status 
       })), or add shouldRevalidate.
  4. frontend/src/App.tsx:115 (low, development only): the router is created 
     twice.
     - The router is built inside a useState initializer, and StrictMode runs
       that twice in development.
     - The router that React throws away still runs its first load and handles
       back/forward navigation, so loaders run twice and it can call
       clearSession on its own.
     - Fix: create the router once (in a ref or at module level), or call
       dispose() on the extra one.
  5. BookmarkDialog.tsx:437-445 and CollectionDialog.tsx:919-927 (low): a failed
     delete shows no error.
     - If the DELETE returns a 5xx or a network error, the confirmation dialog
       stays open on top. The error message belongs to the edit dialog
       underneath, so the user just sees the spinner stop.
     - Fix: close the confirmation dialog when the action result arrives.

  they're the ones users would actually notice.
